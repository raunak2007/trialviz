# trialviz

A backend that turns a natural-language question about clinical trials into a
visualization specification backed by live ClinicalTrials.gov data.

```
POST /query  {"query": "How are melanoma trials distributed across phases?"}

   question ──► interpret ──► retrieve ──► aggregate ──► spec ──► validate ──► JSON
                (model or     (CT.gov v2   (pure         (bar, line,  (citations
                 rules, into   API, paged,  functions,    scatter,     match bars,
                 a closed      cached,      provenance    histogram,   sums match
                 menu)         counted)     per bucket)   network)     records)
```

The model, when one is configured, only ever decides *what to compute* from a
fixed menu. Every number in a chart is counted from registry records or returned
by the registry's own count endpoint, and every bar, point, node, and edge
carries citations to the NCT records that produced it.

## 1. Running it

Requirements: Python 3.11+ and internet access to `clinicaltrials.gov`. An
Anthropic API key is optional; without one the service runs on the
deterministic rule-based planner.

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
cp .env.example .env            # add ANTHROPIC_API_KEY=... to use the model planner
uvicorn trialviz.app:app --reload --port 8000
```

Then:

```bash
curl -s localhost:8000/query -H 'content-type: application/json' \
  -d '{"query": "How has the number of trials for this drug changed per year since 2015?", "drug_name": "Pembrolizumab"}' | jq .
```

* Demo page: open <http://localhost:8000/> (charts via Vega-Lite, networks via d3; click any mark to see its citations).
* Interactive API docs: <http://localhost:8000/docs>. JSON Schemas: <http://localhost:8000/schema>.
* Health: `GET /health` reports which planner is active.

Docker:

```bash
docker build -t trialviz .
docker run --rm -p 8000:8000 -e ANTHROPIC_API_KEY=$ANTHROPIC_API_KEY trialviz
```

Deployed endpoint on Modal (`modal_app.py`; one warm container, secret holds the key):

```bash
pip install modal && modal setup
modal secret create trialviz-anthropic ANTHROPIC_API_KEY=sk-ant-...
modal deploy modal_app.py        # prints https://<workspace>--trialviz-web.modal.run
```

A live deployment for this submission: **(URL goes here after `modal deploy`)**.

Tests (no network needed; they run against a recorded fixture served through a fake API):

```bash
pytest -q
```

Fully offline run of the whole service, including the demo page, against the fixture:

```bash
python -m tests.fake_ctgov_server --port 8600
TRIALVIZ_CTGOV_BASE_URL=http://localhost:8600/api/v2 uvicorn trialviz.app:app --port 8000
```

Environment variables (all optional): `ANTHROPIC_API_KEY`, `TRIALVIZ_MODEL`
(default `claude-sonnet-5-5`), `TRIALVIZ_CTGOV_BASE_URL`, `TRIALVIZ_HTTP_TIMEOUT`
(seconds, default 60), `TRIALVIZ_MAX_CONCURRENCY` (default 4),
`TRIALVIZ_CACHE_TTL` (seconds, default 3600), `TRIALVIZ_LOG_LEVEL`.

## 2. API

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/query` | Answer a question with a visualization spec (the product). |
| `GET` | `/schema` | JSON Schema for the request, response, and error envelopes. |
| `GET` | `/health` | Liveness plus which planner is configured. |
| `GET` | `/examples` | The example questions, used by the demo page. |
| `GET` | `/docs` | OpenAPI UI generated by FastAPI. |
| `GET` | `/` | The demo page. |

Status codes from `/query`:

| Code | `error.code` | Meaning |
|---|---|---|
| 200 | | A visualization was produced. |
| 422 | `invalid_request` | Body failed validation; `details.problems` lists the fields. |
| 422 | `needs_clarification` | The question is answerable in principle but is missing something (which drug or condition, what to compare). `suggestions` lists phrasings that work. |
| 422 | `unsupported_query` | The question needs data this backend does not have (outcomes, eligibility text, participant ages). |
| 404 | `no_data` | The filters matched zero trials. `details.filters` shows what was searched. |
| 502 | `upstream_error` | ClinicalTrials.gov could not be reached or returned an error; `details.url` is the failing request. |
| 500 | `internal_error` | The post-build consistency check failed. This should not happen; it means a bug, not bad input. |

Error envelope:

```json
{"error": {"code": "needs_clarification", "message": "...", "suggestions": ["..."], "details": null}}
```

## 3. Request schema

`POST /query` takes a JSON object. Unknown fields are rejected.

| Field | Type | Required | Validation | Notes |
|---|---|---|---|---|
| `query` | string | yes | 3 to 1000 chars | The natural-language question. |
| `drug_name` | string | no | ≤ 200 chars | Searched in the registry's intervention area (`query.intr`), which expands synonyms and brand names. |
| `condition` | string | no | ≤ 200 chars | Searched in the condition area (`query.cond`). |
| `sponsor` | string | no | ≤ 200 chars | Lead sponsor or collaborator name (`query.spons`). |
| `country` | string | no | ≤ 100 chars | Country name as spelled on ClinicalTrials.gov, e.g. `United States`. |
| `phase` | list of `EARLY_PHASE1 \| PHASE1 \| PHASE2 \| PHASE3 \| PHASE4 \| NA` | no | | Trials listing any of these phases. |
| `status` | list of overall statuses (`RECRUITING`, `COMPLETED`, `ACTIVE_NOT_RECRUITING`, ...) | no | | Any of these statuses. |
| `study_type` | `INTERVENTIONAL \| OBSERVATIONAL \| EXPANDED_ACCESS` | no | | |
| `start_year` | integer | no | 1900 to 2100 | Earliest start year, inclusive. |
| `end_year` | integer | no | ≥ `start_year` | Latest start year, inclusive. |
| `max_trials` | integer | no | 50 to 10000, default 2000 | Cap on records downloaded per series. See [sampling](#sampling-and-exact-counts). |
| `include_citations` | boolean | no | default `true` | Attach citations to every datum. |
| `citations_per_datum` | integer | no | 0 to 50, default 5 | Cap on citations per bar, bucket, point, node, or edge. `citation_count` is always the full number. |
| `count_mode` | `auto \| sample \| exact` | no | default `auto` | How bar heights are counted when the match set exceeds `max_trials`. |
| `planner` | `auto \| llm \| rules` | no | default `auto` | `auto` uses the model if a key is configured and falls back to rules. |

Structured fields are authoritative: when both the question and a field name a
drug, the field wins. They apply to every series of a comparison unless a series
overrides that field, so for "A vs B" questions leave `drug_name` empty and let
the question carry both names.

## 4. Response schema

Top level:

```json
{"visualization": { ...one of six spec shapes, discriminated on "type"... }, "meta": { ... }}
```

The full JSON Schema is served at `GET /schema` and in the OpenAPI document; the
Pydantic models live in `trialviz/schemas/response.py`. What follows is the
contract a renderer needs.

### 4.1 Chart specs (`bar_chart`, `grouped_bar_chart`, `time_series`, `histogram`, `scatter_plot`)

```jsonc
{
  "type": "bar_chart",
  "title": "Melanoma trials by phase",
  "subtitle": "Interventional studies",            // filters and caveats, nullable
  "encoding": {
    "x": {"field": "phase", "type": "nominal", "title": "Phase", "granularity": null},
    "y": {"field": "trial_count", "type": "quantitative", "title": "Number of trials", "granularity": null},
    "color": null,                                  // {"field": "series", ...} on grouped bars and multi-line charts
    "tooltip": ["phase", "trial_count", "citation_count"]
  },
  "columns": [                                      // every key present on every row, so nothing is guessed
    {"name": "phase", "type": "string", "description": "Phase (display label)"},
    {"name": "phase_code", "type": "string", "description": "Raw ClinicalTrials.gov value behind `phase`, or null"},
    {"name": "trial_count", "type": "integer", "description": "Number of trials"},
    {"name": "citation_count", "type": "integer", "description": "Distinct trials supporting this row"},
    {"name": "citations", "type": "string", "description": "Array of Citation objects, truncated to citations_per_datum"}
  ],
  "config": {"sort": "natural", "stacked": false, "value_format": "integer", "y_zero_based": true},
  "data": [
    {"phase": "Phase 3", "phase_code": "PHASE3", "trial_count": 41, "citation_count": 41,
     "citations": [{"nct_id": "NCT01234567", "title": "...", "url": "https://clinicaltrials.gov/study/NCT01234567",
                    "evidence": [{"field": "protocolSection.identificationModule.briefTitle", "value": "..."},
                                 {"field": "protocolSection.designModule.phases", "value": "[\"PHASE3\"]"}]}]}
  ]
}
```

Rendering rules:

* Read field names from `encoding`; never hard-code row keys. `encoding.x.type`
  follows Vega-Lite's vocabulary (`nominal`, `ordinal`, `quantitative`,
  `temporal`). `granularity` is set only on temporal channels.
* `config.sort` is the order rows are already in: `natural` (phase order, time
  order, bin order) or `value_desc`. Do not re-sort.
* `data` rows are ordered. For `grouped_bar_chart` and multi-series
  `time_series` every (category, series) pair is present, with zeros filled in,
  so legends and groups line up without extra joins.
* `citation_count` can exceed `citations.length` (capped by
  `citations_per_datum`) and can be larger than the number of fetched records
  when exact server counts were used (see `meta.retrieval[].count_method`).

Row shapes by type:

| type | row keys (besides `citation_count`, `citations`) |
|---|---|
| `bar_chart` | `<dimension>` (display label), `<dimension>_code` (raw value, only for enumerated dimensions), `trial_count` or `total_enrollment` |
| `grouped_bar_chart` | same as `bar_chart` plus `series` (the entity, or the secondary grouping) |
| `time_series` | `period` (`"2019"`, `"2019-Q2"`, `"2019-04"`), `period_start` (ISO date of the first day), optional `series`, the measure |
| `histogram` | `bin`, `bin_start` (inclusive), `bin_end` (exclusive, `null` for the open last bin), `trial_count`; plus a top-level `bins` object `{"field", "edges", "unit"}` |
| `scatter_plot` | `nct_id`, `title`, `<numeric_x>`, `<numeric_y>`, optional `group`; one row per trial, `citation_count` is 1 |

Dimension row keys: `phase`, `country`, `intervention_type`, `sponsor_class`,
`status`, `study_type`, `condition`, `sponsor`, `intervention`. Numeric fields:
`enrollment`, `start_year`, `duration_months`, `site_count`.

### 4.2 Network spec (`network_graph`)

```jsonc
{
  "type": "network_graph",
  "title": "Sponsor to drug network for melanoma trials",
  "subtitle": "28 nodes, 50 edges, weight = trials in common",
  "encoding": {
    "nodes": {"id": "id", "label": "label", "group": "kind", "size": "trial_count"},
    "edges": {"source": "source", "target": "target", "weight": "trial_count"},
    "directed": false
  },
  "node_kinds": ["sponsor", "drug"],                 // legend order; `kind` of every node is one of these
  "data": {
    "nodes": [{"id": "drug:pembrolizumab", "label": "Pembrolizumab", "kind": "drug", "trial_count": 312,
               "citation_count": 312, "citations": [...]}],
    "edges": [{"source": "sponsor:merck sharp & dohme llc", "target": "drug:pembrolizumab", "trial_count": 88,
               "citation_count": 88, "citations": [...]}]
  }
}
```

Node ids are `<kind>:<normalized name>` and are unique. Every edge endpoint is
present in `nodes`. Edge weight is the number of distinct trials in which both
endpoints appear; node size is the number of trials the entity appears in among
trials that contributed at least one edge. Edge citations carry two evidence
entries, one per endpoint.

### 4.3 Citations

```json
{"nct_id": "NCT05000001", "title": "Brief title", "url": "https://clinicaltrials.gov/study/NCT05000001",
 "evidence": [{"field": "protocolSection.identificationModule.briefTitle", "value": "Brief title"},
              {"field": "protocolSection.contactsLocationsModule.locations[2].country", "value": "France"}]}
```

`field` is the JSON path inside the API study record and `value` is the exact
value at that path (strings verbatim, lists and numbers JSON-encoded). The first
evidence entry is always the brief title for readability; the rest are the
field values that put the trial into that bar, bucket, period, point, node, or
edge. For a country bar the path points at the specific location entry; for a
duration point it includes both dates; for an edge it includes both entity
fields.

### 4.4 `meta`

| Key | Contents |
|---|---|
| `query` | The question as received. |
| `interpretation` | One sentence on how the question was read. |
| `assumptions` | Choices made where the question was open (default time window, restriction to interventional studies, sampled vs exact counts). |
| `warnings` | Data caveats worth surfacing: truncated categories, records missing a value, trimmed networks, failed exact counts. |
| `plan` | The executed `QueryPlan`: analysis, viz type, filters, series, dimension, measure, network kind, numeric fields, granularity, top_n. |
| `filters` | The base `EntityFilter` applied to every series. |
| `retrieval[]` | Per series: effective filter, `total_matching` (registry count), `fetched`, `truncated`, `sample_order`, `count_method` (`sampled` or `exact_server_counts`). |
| `source` | `ClinicalTrials.gov`, API base, `retrieved_at` (UTC). |
| `api_calls[]` | Every request made: full URL (reproducible with curl), status, latency, cache hit, records returned, `totalCount`. |
| `planner` | `mode` (`llm` or `rules`), `model`, `attempts`, `fallback_reason`. |
| `timing` | Milliseconds spent interpreting, retrieving, aggregating, total. |

## 5. How a query is answered

Code map: `trialviz/schemas` (contracts), `trialviz/interpret` (question to
plan), `trialviz/ctgov` (API access), `trialviz/analysis` (aggregation),
`trialviz/viz` (spec assembly and validation), `trialviz/pipeline.py`
(orchestration), `trialviz/app.py` (HTTP).

### 5.1 Interpret: question to `QueryPlan`

The model fills in `PlanDraft` (`trialviz/schemas/plan.py`), a closed menu:
an `analysis` enum (`time_trend`, `distribution`, `comparison`, `geographic`,
`network`, `scatter`, `histogram`, `unsupported`), an `EntityFilter` of
strings copied from the question, enum-valued `dimension`, `split_by`,
`measure`, `network`, `numeric_x/y`, `time_granularity`, a bounded `top_n`,
and for comparisons a short list of series with per-series filter overrides.
The call goes to the Anthropic Messages API with a single tool,
`submit_query_plan`, whose input schema is the `PlanDraft` JSON Schema, and a
prompt that allows no response other than that tool call. The tool input is
snapped onto the enum spellings ("Phase 3" becomes `PHASE3`) and validated by
Pydantic before anything else sees it. A draft that fails validation, or a
reply that is prose instead of a tool call, is sent back to the model once
with the reason; a second failure hands over to the rule-based planner. The
system prompt (`trialviz/interpret/llm.py`) explains the menu, today's date,
and how relative dates resolve, and gives nine worked examples. The model
never sees trial data.

This took two iterations against the live API. The first version used the
grammar-constrained structured-output mode (`output_config.format`); the API
returned `400 Schema is too complex` for this schema, after 20 to 45 seconds
per call, so every request silently fell back to the rule-based planner. The
second version forced the tool with `tool_choice: {"type": "tool"}`, which
the current model generation (Sonnet 5.5, Opus 5.5, Fable 5.1) rejects with a
400. The shipped version uses `tool_choice: auto` plus validation and one
corrective retry. I chose that over flattening the schema to satisfy the
grammar compiler: the nested `filter` and per-series overrides are what make
comparisons expressible, and `meta.planner` records which path produced every
plan, so a fallback is never silent.

`normalize()` (`trialviz/interpret/normalize.py`) turns a draft into an
executable `QueryPlan` and is where the rules live, so they apply identically to
model and rule-based drafts:

* Structured request fields override anything read from the question.
* Phase questions are restricted to interventional studies (observational
  studies have no phase; they would all land in "Not specified").
* Time trends get a closed window: the last 10 years if none was given, the
  current year as the end if only a start was given. The window is applied
  server-side so the sample is drawn from the right years.
* A distribution over start year becomes a time trend; a trend with a
  dimension becomes a split trend; comparisons without a dimension compare by
  phase; a scatter without axes plots enrollment against start year. Each of
  these adds a line to `meta.assumptions`.
* Comparisons must have at least two series that resolve to different filters.
* Every series must name at least one drug, condition, sponsor, country, or
  free-text term. A query that would match the whole registry is refused with
  `needs_clarification` rather than answered from an arbitrary sample.

If normalization rejects a model draft, the error text is sent back to the
model once; if the model is unavailable (no key, auth failure, network, a
refusal, or a schema mismatch), the rule-based planner
(`trialviz/interpret/rules.py`) takes over and `meta.planner.fallback_reason`
says why. The rules are keyword and regex heuristics for the question classes
in the appendix of the assignment; they are deliberately conservative and
return `unsupported` when they cannot tell what to group by.

### 5.2 Retrieve: `QueryPlan` to records

`trialviz/ctgov/params.py` maps an `EntityFilter` onto the v2 API: free text
goes to the search areas (`query.intr`, `query.cond`, `query.spons`,
`query.term`), statuses to `filter.overallStatus`, and countries, phases, study
types, and year ranges to an Essie expression in `filter.advanced`
(`AREA[Phase]PHASE3`, `AREA[StartDate]RANGE[2015-01-01,2020-12-31]`, joined with
`AND`/`OR`). The `fields` parameter restricts each record to the 19 pieces the
analyses need, which keeps page payloads small enough to fetch 1,000 records
per request.

`CTGovClient` (`trialviz/ctgov/client.py`) pages with `pageToken` at 1000
records per page up to `max_trials`, retries 429 and 5xx with exponential
backoff and `Retry-After`, fails fast on 400, caches responses in memory with a
TTL, limits concurrency with a semaphore, and logs every URL into
`meta.api_calls`. Records are fetched sorted by `StartDate:desc`, so a truncated
result is "the N most recently started matching trials", a sample a reader can
reason about.

`parse_study()` (`trialviz/ctgov/records.py`) normalizes a raw record into a
small `Trial` dataclass and keeps the array indices needed to cite the exact
JSON path later (which location entry, which intervention).

### Sampling and exact counts

A filter like "melanoma" matches far more trials than it is reasonable to
download per request. The sample is capped at `max_trials`, and
`meta.retrieval[].truncated` says when the cap was hit. Bar heights computed
from a truncated sample would be wrong, so when a series is truncated (or
`count_mode=exact`) and the chart is a plain count over a dimension the
registry can filter on, the pipeline asks the API for one `totalCount` per
category and uses those as the values. The sample is still used for citations.

Dimensions with exact counts: phase, status, study type, sponsor class,
intervention type, start period (one `RANGE` per year, quarter, or month), and
country (candidates come from the sample's top countries). Phase buckets follow
the registry's display convention, so "Phase 1/Phase 2" is its own bucket and
the Essie expressions are made mutually exclusive (`AREA[Phase]PHASE2 AND NOT
AREA[Phase]PHASE1 AND NOT AREA[Phase]PHASE3`), which is why the bars add up to
the total. Free-text dimensions (sponsor name, condition, drug name) and
anything with a secondary grouping stay sampled; `meta.retrieval[].count_method`
and a line in `meta.assumptions` always say which method produced the numbers.
If the count requests fail, the response degrades to sampled values with a
warning instead of failing.

### 5.3 Aggregate

`trialviz/analysis/dimensions.py` is the registry of dimensions: how to read a
category off a `Trial`, its display labels, whether a trial can fall into
several categories (countries, conditions, intervention types), its natural
order, and the evidence path. `aggregate.py` groups trials into buckets that
keep every supporting trial and its evidence; a trial is counted once per
bucket. `numeric.py` bins enrollment, duration, and site counts on fixed
human-readable edges and builds scatter points. `networks.py` builds
co-occurrence graphs (sponsor to drug, drug to drug, condition to drug, sponsor
to condition, sponsor to collaborator), prunes to the heaviest edges, and
attaches citations to every node and edge.

Drug names are folded by `drugs.py`: dose, route, and parenthetical noise is
stripped, and the registry's own MeSH terms (`interventionBrowseModule`) anchor
brand names and codes to the generic name when exactly one MeSH term matches an
intervention's name or `otherNames`. The mapping is learned from the result set
itself, so "MK-3475", "Keytruda", and "pembrolizumab 200 mg" become one node
without a hand-maintained synonym table. Placebo, sham, and standard-of-care
arms are excluded from drug networks.

### 5.4 Spec and validation

`trialviz/viz/build.py` has one builder per analysis and only reshapes the
aggregation output into rows, encodings, and column docs. Titles and subtitles
are templated from the plan (`titles.py`), not generated. `validate.py` runs
before the response is returned: every row carries the encoded fields and only
documented keys, values are non-negative numbers, citations reference fetched
trials and carry evidence, `citation_count ≥ len(citations)`, network edges
reference existing nodes, and for single-valued untrimmed sampled charts the
values sum to the number of categorized records. A failure is a 500, by design.

## 6. Query coverage

| Question class (appendix) | Analysis | Visualization | Exact counts |
|---|---|---|---|
| "How has the number of trials for [drug] changed per year since 2015?" | `time_trend` | `time_series` | yes |
| "How many trials started each year for [condition]?" | `time_trend` | `time_series` | yes |
| "... per quarter / per month" | `time_trend` with granularity | `time_series` | yes |
| "... over time by phase" | `time_trend` + `split_by` | multi-line `time_series` | sampled |
| "How are [condition] trials distributed across phases?" | `distribution` by phase | `bar_chart` | yes |
| "Most common intervention types / sponsor classes / statuses / study types" | `distribution` | `bar_chart` | yes |
| "Which sponsors / conditions / drugs appear most in [X] trials?" | `distribution` (top N) | `bar_chart` | sampled |
| "Trials by phase and sponsor class" | `distribution` + `split_by` | `grouped_bar_chart` | sampled |
| "Compare phases for Drug A vs Drug B" | `comparison` | `grouped_bar_chart` | yes, per series |
| "Compare sponsor categories across two conditions" | `comparison` | `grouped_bar_chart` | yes, per series |
| "Compare trials per year for A vs B" | `comparison` by start year | multi-line `time_series` | yes, per series |
| "Which countries have the most recruiting trials for [condition]?" | `geographic` | `bar_chart` (top 20) | yes |
| "Network of sponsors and drugs for [condition]" | `network` sponsor_drug | `network_graph` | n/a |
| "Which drugs co-occur in combination studies?" | `network` drug_drug | `network_graph` | n/a |
| condition to drug, sponsor to condition, sponsor to collaborator | `network` | `network_graph` | n/a |
| "Plot enrollment against start year, colored by phase" | `scatter` | `scatter_plot` | n/a |
| "Distribution of enrollment / trial duration / number of sites" | `histogram` | `histogram` | n/a |
| "Total enrollment by phase" | any count analysis with `measure=total_enrollment` | as above | sampled |

Adding a dimension is one entry in `dimensions.SPECS` plus, optionally, one
Essie expression in `exact_counts.bucket_expressions`. Adding a network kind is
one entry in `networks.ROLES`. Adding an analysis type is one builder.

## 7. Design decisions and tradeoffs

**The model chooses from a menu and never touches numbers.** The hallucination
surface of a query-to-chart system is the step where free text becomes
quantities. Here the model's entire output is an enum-valued plan submitted
through a tool schema, then validated and normalized in code. The
cost is expressiveness: a question the menu cannot express is refused with a
reason instead of being approximated. I think that is the right failure mode
for a tool that cites a medical registry.

**Rules as a fallback, not a competitor.** The deterministic planner exists so
the service runs with no key, so tests are reproducible, and so an outage of
the model API degrades to "worse interpretation" rather than "no service".
Both planners produce the same `PlanDraft` and go through the same normalizer,
so all defaults and guards are written once.

**Exact counts over sampled counts when it matters.** The alternative was to
download everything (slow, impolite to the API, and still capped by what a
request can hold) or to present sample-based counts as if they were totals.
Counting per category server-side costs one cheap request per bucket (12 for a
twelve-year trend, 8 for phases) and makes the headline numbers right. The
tradeoff is that citations then come from a sample, which the response states
plainly.

**Sorting by start date when sampling.** Relevance ranking from the registry is
opaque; "the 2,000 most recently started matching trials" is a sample a reader
can reason about, and it makes repeat runs stable.

**Phase buckets follow the registry's display convention.** A trial listing both
Phase 1 and Phase 2 is one "Phase 1/Phase 2" trial, not one of each. That keeps
bar sums equal to trial counts and matches what users see on the website.

**Specific row keys plus an encoding, not generic `x`/`y` keys.** Rows read
naturally in the JSON (`"phase": "Phase 3", "trial_count": 41`), the encoding
tells the renderer which keys to use, and `columns` documents every key. This
mirrors Vega-Lite's shape so a frontend can translate specs almost mechanically
(the demo page does exactly that).

**Provenance is carried through aggregation, not reconstructed after.** Each
bucket keeps `(trial, evidence)` pairs as it is built, so citations are a
by-product of counting rather than a second lookup that could disagree with
the chart. The validator checks that they agree anyway.

**MeSH-anchored name folding rather than a synonym table.** A static table
would be stale on day one. The registry already ships MeSH terms per trial; the
folding learns from them within each result set and does nothing when it is
unsure (one MeSH term must match exactly one intervention).

**Refusing unbounded queries.** "How many trials started each year?" with no
entity would silently chart a sample of a 500,000-record registry. The
normalizer requires at least one search term and returns `needs_clarification`
with example phrasings instead.

**Async, cached, concurrency-limited client.** Series of a comparison are
fetched concurrently; exact-count fan-outs run under a semaphore; identical
requests within an hour are served from memory. The registry publishes no hard
rate limit, so the client is conservative by default and configurable.

Things I decided against: an LLM pass to write titles or narrative (templates
are deterministic and good enough), letting the model emit Essie or URL
parameters directly (too easy to produce a valid-looking filter that means
something else), and a generic `x`/`y` row format (loses self-description).

## 8. Testing and how correctness was checked

`pytest -q` runs 78 tests in under a second with no network:

* `tests/fixtures/studies.json` is a hand-written set of 14 records in the
  exact nested shape the v2 API returns for a `fields`-restricted request,
  built by `tests/fixtures/make_fixture.py`. It deliberately covers combined
  phases, observational studies with no phase, a missing start date, brand and
  code names that fold to one MeSH term, placebo arms, multi-country trials,
  duplicate country entries, and collaborators.
* `tests/conftest.py` implements a fake ClinicalTrials.gov that evaluates the
  real request parameters the client sends, including a small Essie evaluator
  for `AREA[...]`, `RANGE[...]`, `AND`, `OR`, `NOT`, and parentheses, plus
  pagination, `countTotal`, status filters, and `StartDate` sorting. The
  pipeline tests therefore exercise the real client, parameter builder,
  planner, aggregation, builders, and validator end to end.
* Unit tests cover record normalization and phase labelling, parameter
  building, retries and caching, every aggregation path (sums, multi-valued
  dimensions, pair grouping, time buckets and gap filling, drug folding,
  networks and pruning, histograms, scatter), the rule-based planner on all
  appendix queries, the normalizer's defaults and guards, planner retry and
  fallback orchestration with a scripted model, the Anthropic planner with a
  stubbed SDK client (prompt assembly, retry feedback, refusals, API errors),
  and the HTTP layer including every error envelope.
* `trialviz/viz/validate.py` runs on every real response as a last line of
  defense, and the pipeline tests assert that it rejects tampered specs.
* The demo page was exercised in a headless browser against the fake API for
  every chart type, which caught three real bugs (a collapsed chart width, a
  duplicate element id that swallowed citation clicks, and a time axis that
  displayed 2019 as 2018 in western time zones).
* `ruff check` and `ruff format` are clean (`ruff.toml`).
* The first live run against ClinicalTrials.gov confirmed the `fields` piece
  names, the Essie `AND NOT` phase expressions, cursor pagination, and the
  per-category count requests without changes. The one live failure was the
  model planner's structured-output schema rejection described in 5.1, which
  the fallback absorbed (every example still produced a chart) and which led
  to the tool-call implementation.

The example outputs in `examples/outputs/` were produced against the live API
with `scripts/run_examples.py`.

## 9. Limitations and what I would do with more time

* **Entity recognition depends on the registry's search.** "Keytruda" works
  because `query.intr` expands synonyms, but a misspelled drug returns
  `no_data` rather than a suggestion. Next step: resolve names through the
  registry's MeSH tree or a drug thesaurus before searching and surface
  "did you mean".
* **Exact counts cover enumerated dimensions and countries only.** Sponsor
  names, conditions, and drug names stay sample-based when the match set is
  large, as do split and stacked charts. Essie can express those too; it is a
  question of request budget and of deciding how fuzzy text matches should be
  bucketed.
* **Sample bias is stated, not removed.** A truncated network or histogram
  describes the most recent trials. A stratified or random sample would need
  either more requests or a different data source (the bulk download).
* **Network semantics are simple.** Edges are raw co-occurrence counts. Lift or
  PMI-style weights, community detection, and time slicing would make the
  graphs more informative; the node/edge shape already carries what a frontend
  would need.
* **Durations use completion date or primary completion date**, whichever is
  present, and site counts count location entries, which can list the same
  facility twice. Both are documented in the evidence paths.
* **No persistence.** The cache is in-process; a shared cache (Redis) and a
  job queue would be the first operational additions, followed by request
  tracing per `meta.api_calls` entry.
* **Rule-based planner coverage is narrow by design.** It handles the
  appendix's phrasings and common variants; anything unusual should go to the
  model. With more time I would build an evaluation set of a few hundred
  questions with expected plans and run both planners against it in CI.
* **Single-user demo page.** It is a renderer for the spec, not a product.
  A real frontend would keep chart state, allow drilling into citations by
  clicking through to the registry, and compare runs.

## 10. Example runs
